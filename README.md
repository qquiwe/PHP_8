# Звіт (трекер особистих витрат)

Аудит охоплює весь застосунок практикумів №1–7 (`classic/` = класичні форми
практикуму №4, `ajax/` = AJAX-фронтенд практикуму №5, `api/` = REST API
практикумів №6–7). Для кожного класу вразливості — конкретний payload, яким
перевірено, і фрагмент коду.

---

## 1. SQL-ін’єкція

**Ціль перевірки (варіант 13):** фільтр за категорією (`findByCategory`,
`api_list.php?q=...`, `api.php`).

**Payload:** `' OR '1'='1`

**Результат аудиту:** усі SQL-запити в проєкті (практикуми №4–8) вже
використовували `prepare()`/`execute()` з іменованими плейсхолдерами —
жодної конкатенації `$_GET`/`$_POST` в текст запиту знайдено не було, у тому
числі у файловому кеші практикуму №7 (`cachedQuery()` там будувала SQL без
параметрів користувача взагалі). **Нових вразливих запитів не виявлено.**

```php
// в проєкті (ajax/api_list.php)
$stmt = $pdo->prepare(
    'SELECT * FROM transactions WHERE owner_token = :owner AND category LIKE :q
     ORDER BY transaction_date DESC, id DESC'
);
$stmt->execute([':owner' => $owner, ':q' => '%' . $q . '%']);
```

Перевірено вручну: `curl.exe -i "http://localhost:8000/ajax/api_list.php?q=%27%20OR%20%271%27%3D%271"` —
повертає порожній список (жодного збігу), а не всі записи й не помилку SQL-синтаксису.

## 2. XSS (Cross-Site Scripting)

**Ціль перевірки:** поле `category` при виведенні списку.

**Payload:** `<script>alert(document.cookie)</script>` та `<img src=x onerror=alert(1)>`,
введені як назва категорії через форму додавання.

**До аудиту (практикум №4, перша версія `index.php`):** виведення вже було
захищене `htmlspecialchars()`, але без явного `ENT_QUOTES` і без єдиної
функції-обгортки — легко забути в новому місці виводу.

**Після (практикум №8):** уся HTML-генерація йде через спільну функцію
`e()` із `security.php`:

```php
function e(?string $value): string
{
    return htmlspecialchars((string) $value, ENT_QUOTES, 'UTF-8');
}
```

```php
<td><?= e($t['category']) ?></td>
```

Для AJAX-фронтенду (`ajax/script.js`) — аналогічний обов’язковий
`escapeHtml()` перед кожною вставкою в `innerHTML`:

```jsx
function escapeHtml(str) {
    const div = document.createElement('div');
    div.textContent = String(str);
    return div.innerHTML;
}
```

**Перевірка:** додали транзакцію з категорією `<script>alert(1)</script>` —
у `classic/index.php` і в AJAX-таблиці текст відображається як буквальний
рядок `<script>alert(1)</script>`, вікно `alert` не спливає.

REST API (`api/api.php`) віддає “сирий” JSON без HTML — це безпечно саме
тому, що клієнт (`script.js`) сам екранує дані при вставці в DOM; якщо
дані API вставляти в HTML без екранування на стороні клієнта, вразливість
виникне там, а не в самому API.

## 3. CSRF (Cross-Site Request Forgery)

**Ціль перевірки:** форма додавання транзакції — критично для
фінансових даних (сторонній сайт міг би непомітно “дописати” транзакцію від
імені відвідувача).

**До аудиту:** `add.php`, `edit.php`, `delete.php` (практикум №4) та
`api_add.php` (практикум №5), `api.php?action=` (практикуми №6-7) приймали
POST без жодної перевірки походження запиту — досить було зверстати сторонню
HTML-форму, що POSTить на `add.php`, і будь-який відвідувач цієї сторінки,
залогінений (з активною сесією) у застосунок, ненавмисно додав би запис.

**Після (практикум №8):** токен у сесії + приховане поле форми /
поле `csrf_token` у JSON-тілі, перевірка через `hash_equals()`:

```php
// видача токена (усюди, де є форма чи перший AJAX-виклик)
function csrfToken(): string { ensureSession(); return $_SESSION['csrf_token']; }

// перевірка при кожному POST, що змінює дані
function verifyCsrfToken(?string $token): bool {
    ensureSession();
    return $token !== null && $token !== '' && hash_equals($_SESSION['csrf_token'], $token);
}
```

```php
if (!verifyCsrfToken($_POST['csrf_token'] ?? null)) {
    safeErrorHtml('Недійсний CSRF-токен. Оновіть сторінку і спробуйте ще раз.', null, 403);
}
```

**Перевірка:**

```
curl.exe -i -X POST "http://localhost:8000/classic/add.php" `
  -d "amount=100&category=Тест&transaction_date=2026-09-23"
```

(без поля `csrf_token`) → **403 Forbidden**, запис не додається.
З дійсним токеном, узятим із `csrfToken()` цієї ж сесії, — **успішне** додавання.
Токен з іншої/старої сесії так само відхиляється.

## 4. Незахищена дія варіанта 13: перегляд чужих транзакцій за id в URL

**Проблема:** `edit.php?id=N` та `api.php?resource=transactions&id=N`
виконували `SELECT ... WHERE id = :id` без жодної перевірки, кому запис
належить — підставивши в URL послідовно `id=1`, `id=2`, … будь-хто міг
переглянути (а через `edit.php` — і відредагувати) чужі фінансові записи.

**Причина: КП** не передбачали реєстрації користувачів, тож “власника” в попередніх
практикумах не існувало як поняття — усі бачили всі записи.

**Рішення:** введено легковаговий ownership-токен, прив’язаний
до сесії відвідувача (`security.php::currentOwnerToken()`), і кожен запит,
що читає чи змінює конкретний запис за `id`, додатково фільтрує за
`owner_token`:

```php
$stmt = $pdo->prepare('SELECT * FROM transactions WHERE id = :id AND owner_token = :owner');
$stmt->execute([':id' => $id, ':owner' => $owner]);
$row = $stmt->fetch();
if (!$row) {
    // та сама відповідь, що й для "не існує взагалі" - не видаємо факт існування чужого запису
    return resultError("Операцію з id={$id} не знайдено", 404);
}
```

Це НЕ повноцінна автентифікація — ownership-токен живе в PHP-сесії (cookie `PHPSESSID`) без пароля, тож не захищає від крадіжки самої сесії чи від того, що
користувач, який очистив cookies, “втратить” доступ до своїх старих записів.
У реальному застосунку тут був би повноцінний логін і `user_id` з таблиці
`users`, а не анонімний токен.

**Перевірка:** відкрили застосунок у двох різних браузерах (або в
звичайному й приватному вікні) → у кожного своя порожня історія транзакцій;
підстановка чужого `id` в `edit.php?id=...` повертає 404, а не форму з
чужими даними.

## 5. Додаткові знахідки аудиту

| Знахідка | До | Після |
| --- | --- | --- |
| Видалення через GET-посилання | `delete.php?id=N` — виконувалось за самим переходом за посиланням | `delete.php` приймає лише `POST` (405 на GET) + CSRF-токен + `confirm()` на клієнті як додатковий, але не єдиний, захист |
| “Сирі” помилки БД | `die($e->getMessage())` міг показати структуру таблиці | `safeErrorHtml()`/`safeErrorJson()`: деталі в `error_log()`, користувачу — загальне повідомлення |
| Кешований баланс (практикум №7) | Ключ кешу `'balance'` був спільний для всіх відвідувачів — перший запит одного користувача міг “засвітити” свій баланс іншому в межах TTL | Ключ кешу тепер включає `owner_token` (`'balance:' . $owner`) |
| Валідація лише на клієнті | `required` в HTML легко обійти прямим `curl`-запитом | Усі поля (`amount`, `category`, `transaction_date`) валідуються на сервері незалежно від HTML-атрибутів |
